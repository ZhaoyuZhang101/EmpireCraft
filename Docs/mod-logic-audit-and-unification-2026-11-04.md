# 整体逻辑审视、统一意愿与修复优先级

状态：只读排查、隔离复现及实施建议；本轮没有修改游戏实现，没有提交或推送。本次是重点调用链审查，不是全模组无遗漏审计，也没有运行多局游戏平衡模拟。工作区其他任务的改动必须保留。

用户要求：检查整体玩法、可能引起 bug 的地方、逻辑与优化，重点核对同一天下尤其华夏的统一意愿；不能仅有“渴望统一”的文化标签。

## 一、华夏统一意愿：已确认的实现脱节

### 1. 强统一标签没有贯通前现代战略

证据：

- `Locales/Cultures/Culture_Huaxia/CultureRule.jsonc:19` 确有 `political_traits: ["strong_unification"]`；China、Shanhai 同样配置了此标签。
- 读取该特质的 `WarlordEraSystem.HasStrongUnification`，当前主要用于现代建政、军阀时期和 `NationalUnificationSystem.Consider` 的民族统一。
- 前现代 `UnificationSystem.Bars`（约231行）按天下文化线是否为 Huaxia 提供“久乱思治”门槛优惠，没有读取 strong_unification。
- `ClaimAgendaSystem.UnificationUrgency` 已经有针对朋党朝廷的15～25紧迫度，不能再次宣称它完全没有统一议程；但是这也不是文化标签驱动的通用战略。

结论：古代华夏不是完全没有统一机制，而是标签未贯通。拥有标签不会在前现代直接增加统一目标优先级、准备行为或统一提案的持续性。新增自定义文化即使挂该标签，也不能当然获得古代华夏的降门槛待遇。

建议：建立单一的文化统一倾向查询，实际作用于分裂天下的战略目标、准备与议程，并把数值和适用范围配置化。强倾向应提高持续行动意愿，不提供凭空的兵力、免费吞地或无限宣战。不硬编码“只有名字叫 Huaxia 才渴望统一”。

### 2. 只检查占城第一名，第一名受限就跳过整个天下

`UnificationSystem.Yearly` 约812～833行：先按占城数排序，固定 `top = ranked[0]`，随后遇到 `FormerLocked`、`InGrace` 或门槛不满足便 `continue` 到下一个天下。

因此会出现：甲占城最多但仍在前朝冷却，乙已经具备足够份额、兵力和政治条件，程序仍不检查乙。类似地，占城第二而军力遥遥领先的一家，不能通过当前只有第一名才能尝试的军力优势路径启动。

建议：保留候选排序，但对各候选逐一核对资格、占比、其余对手的最高国力、接壤及承受能力，选出合法且有行动能力的一家。候选的对手国力必须从“除自身外所有有效对手”计算，不能继续固定 `Skip(1)`。前朝冷却是限制该家，不应无意中冻结全天下；不要删除其本身的冷却。

### 3. 群雄均势时，“久乱思治”仍可能没有人能启动

当前一般门槛为占40%，或至少8%且国力达到其他对手最大值的2倍；华夏久乱30年后开始逐步放宽，80年时降至占20%或国力1.3倍。

算例：十家各占10%、国力相同，即便乱了80年，也没有一家满足放宽后的条件。这是当前规则的结果，不能简单作为某一局发生 bug 的证据；普通战争本应继续打破均势，但强统一标签没有帮助它为同天下目标持续准备。

建议：把“有统一志向、为统一备战”与“获得正式统一战争资格”分开。均势时也能优先整军、积粮、结盟和攻击适当的同天下目标；取得优势后再进入统一进程。对弱国保留生存选择，避免全天下每年同时发动统一战争。

另查：无帝国法理核心的文化连通天下，`ChaosYears` 因 lead 为 null 返回0，不能获得现有“久乱思治”优惠。如需使开局长期未称帝的华夏也有此动力，应为这种天下设计稳定且可存档的乱世起点；不要用临时连通块编号或每次读档重置的计时器。

### 4. 获得天命、结束统一进程与实际完成统一混在一起

- `TianxiaSystem.BarsContender`：只要共主仍存在，其他国家不能问鼎。
- `UnificationSystem.Yearly` 约771行：统一进程达到30年且占比至少50%，会记录统一完成并结束统一进程。
- 共主之后走 `Pacify`：每年35%机会考虑一家目标；可能先接受对方朝贡并返回，之后朝贡关系又被常规宣战闸门保护。

这些规则分别有维持秩序、限制无限统一战和保护外交关系的目的，但组合起来可能让“共主已经产生，天下仍有大量独立势力”的格局长期持续。

建议：界面和日志分别显示“受命为共主”“本轮统一进程结束”“实际完成统一”。保留既有30年收束规则时，不应把过半版图一概描述成天下已经完全统一。对于强统一文化，共主在恢复军饷和后勤后继续有收复／整合目标；朝贡是外交秩序，不应自动等于政治统一。整合可通过劝并、谈判、正式改隶或合法战争实现，不能直接无视盟约、吞并所有朝贡国。

### 5. 需要核实的运行时阻塞

以下尚不能凭源码判定为某一局的主因：

- 统一候选是否真在同一天下；玩家锁定天下、不同法理及都城在外会影响成员认定。
- 可用国库、欠饷、正在死战、在打战争数、战争可达性及部落共同体关系是否阻止宣战。
- 朝堂提出统一议题后，是否因其他议题排队、反对票或执行时目标变化而失效。
- 统一者挑选首个接壤目标后 `startWar` 失败，是否连续重试同一个失败目标而饿死其他可打目标。

扩展现有 `Diagnose/FormationDiagnostics` 即可：按天下输出当前倾向、候选、份额／门槛、国力比、冷却剩余、阻塞原因、下次复查时间。使用限频和变化触发，不对每个国家每帧刷日志。

## 二、其他已经确认的代码问题

### A. 海上商路的失效端点会令当月结算提前中止

位置：`Scripts/GeneralSystems/TradeRouteSystem.cs:168` 的 `Settle`。

当前顺序：取城市 → `Treaty(city.kingdom, partner.kingdom)` → 才检查 `Tradeable(city/partner)`。城市被毁或失效后，读取 kingdom 会抛空引用。年度建立的 Routes 不会在每月结算前自动清除全部失效记录；最外层捕获异常会结束本次结算，后续商路没有继续处理。

已提取当前生产 `Settle()`，配替身世界对象执行：删除商路目的城市后，稳定得到 `NullReferenceException`。脚本：`C:/Users/zhang/AppData/Local/Temp/empirecraft-trade-audit-20261104.ps1`。这不是游戏内复现。

修复：先验证两端城市及国家，再访问关系；无效商路延后删除或请求重新配对。一个坏端点不能让其他有效商路跳过本月。同步检查城市易主、失去码头、同国化、封锁和条约失效。

### B. 条约互指商路会重复结算双方收益

位置：同一 `Settle()` 约182行。正常每条有向记录只 `Earn(city)`，条约商路额外 `Earn(partner)`；A→B和B→A同时存在时，双方各结算两次。

同一隔离脚本结果：普通互指商路收益为10、10；仅切换为条约关系后变20、20。现有注释表达“胜者也得利”，没有将这个重复计数定义为显式条约倍率。

修复前明确结算单位：若每条无向商路双方各获一次收益，用当月端点对去重；若按有向服务计酬，则移除额外的反向发放，并保证只有单向配对时条约双方的收益规则仍合理。不要去重后误删第三个港口的独立商路。

### C. 手动军及澳宋募兵没有扣除在外先遣队兵力

位置：`CorpsSystem.cs` 约654～706行，以及 `TransmigrantSystem.Growth.cs/Recruit`。

普通军补员使用 `strength + away`；手动军单独补员分支只看本队 `strength < full`。`Detach` 从母队抽出兵力，`Rejoin` 又直接加回，且不调整母队满编。澳宋的 `Recruit` 同样用 `full - strength` 算缺额。

算例：满编1000人的手动军分出400人，母队600。在补给和兵源充足时按现有每月8%补入80人，母队加先遣队已有1080人；继续补可到1400，归建仍保留超编。新增的人来自实际征募，并不是已经证明凭空复制人口；错误是分遣造成不应有的补员缺额和超编。

修复：建立所有补员入口共用的有效缺额计算，计入所有有效分遣队；覆盖手动军、普通军、澳宋跨国募兵及重整入口。只有真实损失才允许补上，合并时保持人员来源、组织度和经验；不要简单裁掉超编人员而损失人口。

### D. 伏波军用枚举大小误识别

位置：`TransmigrantSystem.Growth.cs:239`。`arm >= Rifle` 会把数值排在后面的炮兵、机械化、坦克及航空等手动军也作为伏波军候选。枚举顺序不是建制身份或战力排序。

修复应与新军制标记衔接，不能仅将比较改成等于步枪，因为伏波军本来可以有不同兵种。旧档先保守识别，不把所有手动步枪军都强制改为伏波军。

### E. 战中占领回退另见专项

同阵营换主攻国被误判反攻，以及连续收复丢失 Free 标记，见 `Docs/war-territory-rollback-investigation-2026-11-04.md`。无人区关闭不能排除这两条路径；截图的版图缺口仍需区分实际归属改变与绘制清色。

## 三、整体优化：优先完成现有系统之间的连接

1. **原因可见、行动有反馈。** 把现有日志诊断用于称帝、统一、补员、改革与建设界面的锁定原因。显示最主要的几项原因和可行出路；不是把全部公式堆给玩家。
2. **权力边界统一。** 每项动作明确由城市、成员国、中央、宗主还是文化决定。文化提供倾向与名称，政体决定权力结构，制度解锁能力；手选政体、文化转换和现代化不能互相覆盖到反复切换。现有模型边界修复要保留，不重复给澳宋套王朝周期。
3. **经济从账面产值接向实际供应。** 现有财政README已明确企业税基和成本链尚需完善。复用账本、市场、工厂与预算，不再造平行货币。观察军工原料、交付、工资、销售、税款是否来自同一批实际交易；避免重复产出或同一产值多次变现金。澳宋既有保障属于过去用户的明确要求，不能以平衡名义静默删除。
4. **统一后的治理仍有目标。** 将道路、边疆补给、地方财政、人才培养和接管新区做成可观察进程；改革能降低具体问题，而不是只多几项抽象百分比。已有危机保护 `UpheavalGuard` 及分裂进程应继续共用，避免叠加多套年度随机分裂。
5. **文化差异进入规则与呈现。** 军制身份、番号、派系学说、官职、建筑命名分开配置，提供继承和缺项回退。参考澳宋专项规格，不把不同文化都套成华夏文官、西方封建三派或同样的现代营。
6. **玩法自动运行并可干预。** 治理、补给、训练和改革默认由AI处理，玩家能从少量关键入口调整优先级、预算与目标；不要求逐城逐月手动操作。
7. **性能按场景量测。** 世界规模、城数、军团数、战争数、开启图层与后台日志分别记录。复用既有分帧与缓存，关注年度扫描峰值、交战占领刷新及UI重建；不为优化每帧耗时而改变同一游戏年份内的结算次数。跨世界、读档与模式切换必须让缓存正确失效。
8. **维护可重复的回归集合。** 修复失效测试夹具，优先验证人口／现金／兵员守恒、部队编号、开关与旧档迁移，以及战争全流程。源码片段测试有用但不能代替完整流程与游戏内验证。

## 四、Claude 实施顺序与验收

先修已确认的回退、商路空引用、重复收益和分遣补员；每项做小范围提交。随后修统一候选选择并让文化统一倾向贯通前现代战略，再落地通用军制和澳宋专属玩法。不要同时大改战争、财政和人口数据结构。

统一专项至少验证：

- 同一初始世界、相同开关，带与不带 strong_unification 的对照；比较的是战略目标选择与实际行动，不能只看最终颜色。
- 最大一家受前朝冷却、第二家合格；最大一家处于保护期；占城第二家军力显著领先；同占城数时稳定选取且不饿死其他候选。
- 十家均势、长期无帝国核心、南北两强、共主只占过半、同天下朝贡国、玩家手动拆分天下及跨文化占领本天下的城。
- 亏空、补给不足、玩家禁止外交／扩张、部落共同体、盟约和正在死战时，不以“渴望统一”为由绕过硬约束；资源恢复后会重试。
- 继承、改朝、读档和现代化不会重置已积累的乱世年数或突然制造多场统一战；已有军阀时期与古代统一口径衔接。
- 区分事实统一、附庸归属、朝贡秩序、天命与统一战役收束；界面提示和统计口径一致。

长期平衡按多地图、多开局和多次运行统计：首次统一年数、统一后持续时间、碎裂与重新统一次数、战争间隔、各文明生存率、财政与兵力。不能凭一局反馈或离线编译通过宣称已平衡；也不追求每个剧本强行得到相同历史结局。

构建要求：`dotnet build EmpireCraft.csproj --no-restore`，另做针对本次修改的回归；分别报告静态检查、隔离执行、完整测试与进游戏验收状态。本轮临时脚本只复现当前商路行为，不是修复后的测试。
