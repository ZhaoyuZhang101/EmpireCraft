## 二、当前实现为何缺乏玩法

1. `TransmigrantSystem.cs/Naturalize` 每年把部分外族背景人口改为 Aosong 文化，没有独立归化身份、培训阶段与岗位资质；`NaturalizedPopulation` 因而不能直接作为合格技术工人、干部、精兵人数。
2. `TransmigrantSystem.cs/Publish` 只有按科技时代、分支筛选后向接触文化增加科技进度。内部读者权限、资料借阅、来源保密、人员接触与岗位教育没有形成一套系统。
3. 当前穿越状态 `TransmigrantState` 没有女仆／生活秘书培训和分配数据。名册中的相关官职不代表机制已经存在。
4. `TransmigrantSystem.Growth.cs/Fubo` 通过“手动军、非民兵、兵种数值不小于 Rifle”找第一支部队，并非明确的伏波军建制。`Arm` 枚举顺序也不是战力高低顺序，用大小比较存在误识别风险。
5. `KeepArmy` 主要按人口算满编，`Recruit` 直接补入；没有分别表达伏波军、国民军、治安军的组织身份及培养路径。
6. `CorpsData` 已有 `arm/post/militia/manual/order_id/parent_id`，以及兵力、组织、补给、老兵经验和来源记录，可复用。已有军镇类别不等于完整军制身份，`manual` 是玩家操作属性，不能当作正规军身份。
7. `CorpsSystem.Name` 基本只有全国通用军号；`NextSerial` 使用王国统一递增计数。兵种已经影响速度、费用和火力，不应描述成“所有兵种都没作用”；缺少的是建制、准入、任务和番号之间的关联。

## 三、共用军制框架，先于澳宋特例

把下列维度分开，禁止用一个枚举同时承担全部含义：

- 建制身份：谁组织、谁指挥、谁出钱、服役与退伍规则是什么；由政体、文化、制度和发展阶段提供配置。
- 战斗兵种：步兵、骑兵、炮兵等，继续使用兼容旧档的 `CorpsArmSystem.Arm`。
- 编制层级：营、连、中队或各文化适用的单位；第一期只保存与当前地图单位相对应的层级，不凭名字虚构已经实现的完整军团树。
- 作战／驻防任务：野战、守备、护路、护送、接管支援、训练等；这些任务不是固定兵种。
- 隶属与经费：中央、地方、领主、部族、骑士团等实际主体。显示的上级必须与指挥、补员、财政逻辑一致。

配置按“特殊组织与阶段 → 本国有效军制／制度 → 政体和文化默认 → 通用回退”解析；政体提供默认值，文化提供名称与传统，制度和科技决定哪些编制能用。不能对每个政体硬塞完全相同的三档军队。

覆盖范围至少包括现有律令、封建、游牧、游牧封建、阿拉伯、幕府、古典共和、现代共和、殖民与穿越配置。各类先复用已有兵役、宗主、骑士团与禁军系统，明确谁实际控兵。文化与时代缺乏出处的特色称呼先用保守通名，不把华夏或西方称谓套到所有文化。

每种建制配置必须同时影响：兵源资格、成军／补员速度、训练与骨干需求、经费、装备准入、任务选择和指挥权。区别不能只存在于名称、描述或一个固定战力倍率。

AI 按威胁、驻防缺口、后勤和财力选择编制。地方守备军可以在紧急时参战，但其离岗会造成守备缺口；不要无条件禁止，也不要把所有地方军自动抽到远征前线。治安任务与警察工作区分，复用城市稳定与叛乱系统，避免平行结算两次。

## 四、兵种编号与部队番号

用户要求同时覆盖可见编号和持久化兼容。

1. 保存唯一部队 `id`、建制类型、建制内番号、编制层级、必要的上级／编成区域；`arm` 仍单独保存。编号范围由配置明确：全国、军种／建制、地区等，不强行全球唯一。
2. 番号模板由文化／军制提供。澳宋可依正文层级显示“伏波军第 3 步兵营”“国民军广州第 2 中队”；这些示例不能让每个地图军团不论规模都显示为营或中队。随机地图没有广州时使用本地真实地名。炮兵等按其自身编制编号。
3. 同一编号范围分配单调递增且持久化的计数，旧档先扫描已占用号码再分配。合法不同范围重复数字时，完整番号应能区分；同范围不能重号。
4. 换装保留组织番号和履历。若名称包含已经失实的装备类型，可以更新该描述部分，不改变部队身份。跨兵种改编或建制转隶必须是显式事件，有历史记录和必要的重新整训。
5. 临时渡海分队继承母部队组织信息，以“某部先遣队／第 1 分遣队”等后缀区分；不占正式编制新番号。合并后注销临时标识，不复制兵力、装备与来源。
6. 被俘、改隶、国家合并和分裂按明确规则保留原番号或正式改编，记录旧称。不要每次渲染按当前文化或政体重新掷名字。
7. 军团列表、地图提示、定位反馈、战报、补员／裁撤历史使用同一名称服务。简名与全名同源，长名字不挤坏兵牌。
8. 自定义配置允许调整名称模板、编号范围、起始号、数字格式、层级称谓、兵种显示词；示例、错误提示、缺项回退写进文档。UI 的文化切换不改写内部 ID。
9. 现有 `Arm` 存档数值固定为 0～13：Infantry、Archer、Chariot、Cavalry、Musket、Rifle、Artillery、Mechanized、Tank、Helicopter、Fighter、Bomber、Militia、HeavyArtillery。不得插入或重排；新兵种追加或使用有版本的稳定 ID 迁移。新建制不能塞进这个枚举。

## 五、澳宋：让人口培养接上生产、军队和治理

### 归化民

- 归化身份独立于文化、职业、受教育程度、忠诚和元老资格；不能“讲同样语言 = 已归化”，也不能归化后自动获得元老席位。
- 以收容登记、检疫安置、基础教育、工作分配为可观察流程；这些流程名称为游戏抽象，各阶段显示人数、容量、耗时、费用和停滞原因。
- 从受训人口中培养工人、军人、行政干部、教师和护理人员；这些是岗位／资格，并非相互排他的世袭阶层。留出未受训居民与本地社会。
- 新区治理需要干部、驻防、粮食和交通接续。攻占不会自动带来同额的可用干部与熟练工。培训与住房投入能解决瓶颈，不能只有惩罚。
- 元老身份及后代继承继续走已有席位系统；生活秘书、归化民干部即使亲近元老，也不自动变成元老。

### 女仆／生活秘书

- 做有来源、培训、结业、候补、派遣、在岗及离岗／转训记录的系统，与元老席位或具体成年人绑定；普通服务人员不全部叫女仆。
- 将家政、语言、卫生、识字与文书技能作为培养内容，财政和师资实际消耗。生活秘书服务影响该元老的生活保障和可用精力，限制收益，不能按人数无限叠加全国增益。
- 区分早期女仆学校与后续女子文理学院改制。保留学员积压、职业分流及办公厅管理的矛盾；原著中提案先作为可审议事项，不自动当成已立法。阶段由制度与条件推进，不硬绑随机地图的绝对年份。
- 展示人物履历、岗位、派遣关系和法律身份，婚姻、亲子与席位继承分开接入现有系统。第一期的人物服务与派遣只面向成年人，不把学校未成年学生直接作为可派遣生活秘书。
- 元老工作、学习培养和办公厅开支间形成取舍；转岗后原岗位腾空，不能一人同时作为学生、满额工人、生活秘书和干部重复产出。

### 知识管控

- 至少区分面向社会的教材与出版、岗位所需专业资料、内部政务信息、旧时空来源及敏感资料。分类与授权规则为游戏抽象，不冒称原著有同名四级法令。
- 读取资格按对象、岗位、组织授权和内容判定；内部阅读范围采用《余波》中明确的刊物差异。生活秘书身份不等于任意读取元老全部资料。
- 普通归化民可接受基础教育，受训人员可获得岗位技术；扩大教育和授权提高人才供给。秘密性、办事效率、师资与审查成本之间有取舍，严控不能无成本、万能地消除外流。
- 防止旧时空资料及物品外泄，与维持“澳洲来历”叙事分开于普通军工技术保密。采用正文明确存在的通知与回收措施，不将被驳回草案变成默认法律。
- 对外出版使用逐项内容标签及放行记录，不仅靠科技分支黑名单；不是所有军事题材和政治材料在所有对象面前都绝对禁止。
- 审计 `TechnologySystem.CountContactsKnowing/GetDiffusionDiscount` 等接触传播路径：目前“接触到掌握科技的文化”即可获得折扣，未使用 `released_techs` 做逐项放行。需要区分知识存在、可接触资料和实际泄漏；不能只改 Publish 后声称管控完成。
- 管控限制的是来自该来源的资料传播，不封死其他国家独立研究或从第三方获得的知识，不回收别人已经学会的科技。

## 六、澳宋军队的实际差异与演变

| 建制 | 原著约束 | 应落实的玩法（设计建议） |
| --- | --- | --- |
| 伏波军 | 正规陆海军体系；有营连、骨干扩编、工炮及后勤配套；不能只是一支“首个手动步枪军” | 明确标记陆军建制，培养合格兵员及士官；扩编分出骨干，新兵冲淡经验，训练和军工限制成军速度。野战、要点夺取与远征优先，陆军和已有海军系统衔接而非重复建舰队。 |
| 国民军 | 人民保安体系；地方行政可调动；新区有吸收降丁、整训及治安战任务 | 地区化编成、驻防、护路和接管支援；吸收本地兵源必须登记及整训。不是一改名就具有伏波军训练和装备。可应急参战，必须计算地方离岗缺口。 |
| 治安军 | 特定发展阶段存在，整备时撤销番号，外籍和民族连并入国民军 | 早期来源及身份差异与整编事件；保留人员、经验、装备、原隶属与旧番号履历，迁入国民军。不能删除旧军后免费生成满编新军。具体早期编成与武器在补齐正文依据前不写死。 |

不得把它们当成“步兵／骑兵／炮兵”同层级的兵种，也不得认定国民军就是所有时代的低级伏波军。晋升、转隶、扩编通过正式规则进行，不因兵力够了或更换一把枪自动改变身份。

用一个完整循环检验是否有玩法：收容人口 → 教育与训练 → 工厂／干部／军队配置 → 工业和补给支撑作战 → 国民军与干部接管新区 → 新区提供人口和市场 → 再投资培养。生活秘书分配、内部授权、部队整编应在这个循环中有可见影响。

## 七、给 Claude 的实施顺序与交付要求

1. 先检查工作区已有大量未提交改动，保护其他任务。不要整体还原、格式化、打包提交或推送。先完成仍在排查的战中领土回退修复，再按以下模块推进。
2. 第一批：通用军制身份、持久化番号与命名配置，接入创建、补员、编制调整、分遣合并、解散、存读档、AI 和已有军事 UI。先保留旧战力模型，只逐步替换重复或错误识别。
3. 移除 `Fubo` 按兵种数字大小与手动属性识别建制的做法。旧档迁移需要可追溯证据，不能把所有手动步枪军都改成伏波军；无法唯一确定时保守保留并提供显式整编入口。
4. 第二批：归化身份与受训资格模型。可评估人口组维度或有来源的关联名册，但必须贯通 `Census`、合并、迁移、征募、损失、复员及实体／背景人口切换。先完成数据一致性，再连军制准入与建设岗位。
5. 第三批：生活秘书与培训改制、知识授权与出版传播。新增专属页面须有入口、有按钮、有实际执行反馈和原因显示，不能仅补本地化或制度描述。元老院页面继续复用现有 UI。
6. 第四批：项目和干部约束、军工供应与整编决议。拥有知识和具备量产能力分开，避免现有工业、市场、训练、补给加成多处叠加。不要未经核对就删除以前用户要求的元老保护、初期科技与生存保障；应明确这些是既有游戏规则，原著还原另有依据。
7. 所有速率、容量、成本、编号模板、兵役准入和阶段条件尽量配置化。默认自动运行适合观察型玩法，玩家可在现有界面干预，不要求每个城每月手点。

验收至少覆盖：

- 其他政体也能看到并实际使用差异军制；相同兵种在不同建制中确有不同任务和培养／经费规则。
- 文化或政体变化、换装和反复读档不造成重号、身份丢失或部队履历重置；古代单位不因通用模板全变成现代步兵营。
